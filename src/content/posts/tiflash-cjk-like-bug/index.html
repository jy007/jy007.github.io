在一次针对 TiDB 的正确性测试中，撞见一个让人不敢相信自己眼睛的现象：同一张表、同一条中文模糊查询，默认执行返回 0 行；加一个提示让它换个引擎执行，返回正确的结果。没有报错，没有警告，就是安静地少了所有数据。

-- 默认路由到 TiFlash：错误地返回 0
SELECT COUNT(*) FROM t WHERE s LIKE '%报告%';        -- 0 ❌

-- 强制走 TiKV：返回正确结果
SELECT /*+ READ_FROM_STORAGE(TIKV[t]) */ COUNT(*)
FROM t WHERE s LIKE '%报告%';                         -- 4 ✅

日文「議事録」、韩文「보고서」同样中招，英文却完全正常。这篇文章记录从这个症状一路挖到源码级根因的过程——最后发现，罪魁祸首是 C++ 里一个字节的符号。

先补背景：TiDB 和 TiFlash 是什么关系

TiDB 是一个"计算与存储分离"的分布式数据库：TiDB server 只负责 SQL 的解析、优化和路由，数据存在下面两种引擎里。TiKV 按行存数据，是唯一的权威数据源，所有写入都进它；TiFlash 是从 TiKV 异步复制出来的一份按列存的只读副本，专门加速分析型查询。它们不是二选一，而是"一份数据、两种物理形态"，每条查询去哪边读，由优化器按代价自动决定。

图里三个要点：写入箭头只指向 TiKV（TiFlash 永远不接受写入）；TiKV 到 TiFlash 之间是异步同步，复制时顺便把行格式转成列格式；TiDB 对两边各有一条读取通道，走哪条由优化器决定。

顺着一条数据走一遍就明白分岔在哪。一行包含"报告"二字的文本写入后进 TiKV，事务提交即返回——TiFlash 全程不参与；随后 TiFlash 在后台把这行数据搬过去存成列格式，通常毫秒级完成。等到执行 COUNT(*) ... LIKE '%报告%' 时，优化器一看没有索引可用、要全表扫描加聚合，列存扫得快，于是选了 TiFlash。TiFlash 用它自己的 C++ 代码对每行求值 LIKE——bug 就藏在这一步。而加了提示强制走 TiKV 时，是 TiKV 里另一套独立实现的代码在求值同一个表达式，所以结果正确。

症状全景：交叉验证画出的包围圈

查询TiFlashTiKV期望
LIKE '%报告%'0 ❌4 ✅4
LIKE '%議事録%' / '%보고서%'0 ❌✅命中
英文 LIKE '%report%'✅✅—
LIKE BINARY '%报告%'4 ✅✅4
INSTR(s, '报告') > 04 ✅✅4

这组对照非常有信息量：只有"大小写不敏感的排序规则（utf8mb4_general_ci）+ 中日韩字符 + TiFlash"这个组合出错。LIKE BINARY 换成了二进制比较、INSTR 是另一个函数、TiKV 是另一个引擎，全都绕开了问题。包围圈收得很小：问题出在 TiFlash 里专门处理"大小写不敏感 LIKE"的那段代码上。

把源码挖出来验证

TiFlash 是开源的。把出问题环境对应的稳定版代码中负责这条路径的部分（含真实的 6 万多项字符权重表）原样抽出来单独编译运行——结果全部正确，稳定版没有这个 bug。但出问题的环境跑的是更新的代码。再对比最新的开发版代码，发现 2025 年 9 月合入的一个性能优化（PR #10400）给大小写不敏感匹配新增了一条"纯英文快速通道"，判断是否纯英文的代码是：

auto c = pattern[i];   // c 的类型是 char
if (c < 0)             // 中文字符的每个字节值都很大（≥ 0x80），
    return;            // 当成有符号数看就是负数 → 检测到非英文，放弃快速通道

坑在这里：C++ 标准没有规定 char 带不带符号，这由 CPU 平台的规范决定。x86 服务器上它有符号，ARM 服务器（Linux）上它无符号。拿"报"字的第一个字节 0xE6 来说：

字节 0xE6 在两种平台上的值：
  x86 服务器：  被当成 -26  →  "小于 0" 成立       →  正确识别出中文 ✓
  ARM 服务器：  被当成 230  →  "小于 0" 永远不成立  →  被误认为英文 ✗

把新版代码同样抽出来，分别按两种符号规则编译，症状精确复现：按 x86 规则编译，所有测试用例全过；按 ARM 规则编译，所有中日韩用例全部返回 0，英文用例正常——和线上观察到的现象一模一样。而出问题的环境，机器正是 ARM。

走错通道之后是连环出错：程序拿 230 去查一张只有 128 格的英文权重对照表，读到了表格外面不属于它的内存（用内存检查工具 AddressSanitizer 实测证实）；更致命的是，匹配用的两张内部表一张按"字"记录（'%报告%' 记成 4 项）、一张按"字节"记录（记成 8 项），用同一个下标去访问，长度对不上，越比越乱。最终每一行都被判成"不含报告"。而这个错误结论被当成了最终答案——既不报错，也不换回那条慢但正确的老路——于是查询安安静静地返回了 0。

三个教训

两套代码，两种命运。同一句 SQL，在 TiKV 里是一套代码算的，在 TiFlash 里是另一套人重写的。两边结果一致全靠人工保持同步，任何一边加个优化，都是新的出错机会。所以给表加了 TiFlash 副本之后，关键查询要在两个引擎各跑一遍、比对结果，确认一致再依赖它。

"在我机器上没问题"不等于没问题。这段代码在开发和测试用的 x86 机器上全绿，一部署到 ARM 机器就坏。char 的符号问题是 C/C++ 最经典的平台差异陷阱之一，而测试恰好没覆盖"ARM 机器 + 中文搜索词"这个组合。

最危险的错不是报错，是不吭声的错。快速通道失败时，本该说"我搞不定，换老办法重算"，它却直接说"没找到"。少了这层兜底，一个底层字节问题就原样变成了查询结果里的错误数据。

影响面与规避

  • 受影响：包含该优化的新版本代码（2025 年 9 月之后），且仅限 ARM 机器上的部署。全部 5 种大小写不敏感排序规则（general_ci、unicode_ci、0900_ai_ci 等）都在射程内。
  • 不受影响：不含该优化的稳定版（如开源 v8.5.x 系列），以及所有 x86 部署。
  • 规避：含中日韩字符的 LIKE 查询加 /*+ READ_FROM_STORAGE(TIKV[表名]) */ 强制走 TiKV，或改写为 LIKE BINARY。
  • 修复思路：把字节判断改为 static_cast<unsigned char>(c) >= 0x80，不再依赖 char 的平台符号性，并在 ARM 环境的持续集成里补上中日韩用例。
