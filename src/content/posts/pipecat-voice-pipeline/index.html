整理 Pipecat 单机器人语音场景(如 examples/getting-started/06-voice-agent.py)的分层结构、端到端时序、每个模块的输入输出,以及流式处理各环节的具体参数。

分层结构

从进程生命周期到单轮对话回路,三层容器逐级收窄。

WorkerRunner  管理进程生命周期(SIGINT/SIGTERM)、注册/驱动 Worker
  └─ PipelineWorker(单机器人的常见形态)
       Transport.input()  用户麦克风/通话接入
         → STT                       语音 → 文本
         → UserContextAggregator     拼装用户消息到对话历史
         → LLM                       推理生成回复,可能触发 Tool
         → TTS                       文本 → 语音
         → Transport.output()        下发音频给用户
         → AssistantContextAggregator  把机器人说的话写回对话历史
              ↳ 更新对话历史,供下一轮 UserContextAggregator 使用
  • Frame(src/pipecat/frames/frames.py)是流转的最小单位:音频/文本/控制信号,沿管线下行(DOWNSTREAM,用户→机器人回复方向)或上行(UPSTREAM,错误/打断/就绪信号回传)。
  • FrameProcessor(src/pipecat/processors/frame_processor.py)是所有节点(Transport、STT、聚合器、LLM、TTS)的基类,每个节点收到帧、处理、往下(或上)推。
  • Pipeline(src/pipecat/pipeline/pipeline.py)只是把一串 FrameProcessor 首尾相连。
  • PipelineWorker(src/pipecat/pipeline/worker.py)是"运行时容器",负责启动/结束/心跳/错误处理,是真正跑在 WorkerRunner 里的单元(PipelineTask 是它的旧名字,已弃用)。

端到端语音流程

以用户说"今天北京天气怎么样"、机器人调用天气工具后回答"今天北京晴天,气温25度"为例。

  1. 用户开口 — Transport(Daily/WebRTC/WebSocket/本地麦克风)采集音频帧,VAD 检测语音起止。
  2. STT 把音频帧转成文本帧。
  3. UserContextAggregator 把用户文本追加进共享的对话历史(LLMContext)。
  4. LLM 读取对话历史,流式生成回复文本,期间可能调用 @tool 触发 Function Calling。
  5. TTS 把 LLM 输出的文本流式合成为音频。
  6. Transport.output() 把音频下发给用户播放。
  7. AssistantContextAggregator 把机器人已说出的内容写回对话历史,供下一轮使用。
  8. 用户打断机器人说话时,任意节点可 broadcast_interruption() 广播打断信号(上行+下行),清空未播放的 LLM/TTS 输出,重新进入用户轮次。

各模块的输入 / 输出

沿用上面的例子,串一遍每个模块实际收到什么数据、往下游/给用户返回什么数据。

模块输入输出
Transport.input()
接入麦克风/通话线路		 用户对着麦克风/电话说话产生的原始 PCM 音频字节流(例如 16kHz、16-bit,每 20ms 一帧),外加连接控制信号(开始/结束通话)。 重采样、降噪后,连续往下游发送同样格式的音频数据块,相当于把"用户正在说的话"实时喂给语音识别模块。
STT
语音识别		 上一步的原始音频字节流(用户说"今天北京天气怎么样"对应的那段 PCM 数据)。 先吐出不断修正的中间结果(如"今天"→"今天北京"→"今天北京天气"),用户说完后给出最终文本"今天北京天气怎么样"。
UserContextAggregator
拼装用户输入		 STT 给出的文本"今天北京天气怎么样"。 把这句话追加进完整的对话历史列表,再整体传给 LLM。
LLM
推理生成回复		 完整对话历史列表(系统提示 + 历史对话 + 用户这句新提问)。 一边推理一边流式吐出文字片段;判断需要查天气时,先输出结构化工具调用请求,拿到结果后再生成最终回复文本。
TTS
语音合成		 LLM 吐出的文本片段,如"今天北京晴天,气温25度"。 把文字合成为一段音频字节流(例如 24kHz PCM),连续播放即是机器人用语音说出这句话。
Transport.output()
下发给用户		 TTS 生成的这段语音音频字节流。 通过 WebRTC/电话线路/扬声器真正播放出声音,用户听到机器人说"今天北京晴天,气温25度"。
AssistantContextAggregator
记录机器人说过的话		 机器人这一轮实际说出的完整文本"今天北京晴天,气温25度"。 把这句话作为一条 assistant 消息追加进对话历史,供下一轮用户提问使用。

用户这句话被拼进对话历史后传给 LLM:

[
  {"role": "system", "content": "你是一个语音助手,回答要简短口语化"},
  {"role": "user", "content": "今天北京天气怎么样"}
]

LLM 判断需要查天气,先发出工具调用请求,拿到结果后生成回复:

{"name": "get_weather", "arguments": {"city": "北京"}}
→ {"temperature": 25, "condition": "晴"}
→ "今天北京晴天,气温25度"

机器人说完这句话后,写回对话历史,供下一轮使用:

[
  {"role": "system", "content": "你是一个语音助手,回答要简短口语化"},
  {"role": "user", "content": "今天北京天气怎么样"},
  {"role": "assistant", "content": "今天北京晴天,气温25度"}
]

流式处理细节

整个链路是流式的,但不同环节的"流"粒度不一样:音频采集/播放是固定时间切片,STT→LLM 是"整句攒完再发",LLM→TTS 才是真正按语义(句子)流式传递。

音频采样 / 分片间隔

参数数值
本地麦克风采集分片(transports/local/audio.py)20 ms
音频播放下发打包(4 × 10ms 块)40 ms
STT / VAD 常用采样率16 kHz
TTS 输出常用采样率24 kHz

16kHz 下,20ms 对应 320 采样点 / 640 字节。

VAD 识别机制

VAD 不是简单的能量检测,而是神经网络模型判定(Silero VAD,ONNX 模型,src/pipecat/audio/vad/silero.py):每次喂给模型 512 个采样点(16kHz 下约 32ms)做一次推理,同时计算指数平滑(系数 0.2)后的音量值,关键阈值如下:

  • 置信度 ≥ 0.7(VAD_CONFIDENCE)
  • 音量 ≥ 0.6(VAD_MIN_VOLUME)
  • start_secs 0.2s
  • stop_secs 0.2s

状态机大致是:

  • QUIET → STARTING:单帧(约 32ms)检测到语音;若语音随即消失且未满 0.2s,退回 QUIET。
  • STARTING → SPEAKING:连续 0.2s(start_secs)保持语音判定,触发 UserStartedSpeaking。
  • SPEAKING → STOPPING → QUIET:检测到静音后先进入 STOPPING;若静音未满 0.2s 又出现语音,退回 SPEAKING;连续静音满 0.2s(stop_secs)才触发 UserStoppedSpeaking。

这个"连续一段时间"的去抖动设计是为了防止呼吸声/短促噪音误判成语音起止。

STT → LLM:整句提交,不是分片流式

STT 识别过程中的中间结果(interim transcript)会被 LLMUserAggregator 直接丢弃,不进对话历史。只有 STT 给出的最终确定文本才会被累积到缓冲区。

缓冲区何时提交给 LLM,由用户轮次结束策略决定:默认是基于语义的轮次检测(LocalSmartTurnAnalyzerV3),也可以配置成"静音超时"策略(默认 0.6 秒没有新语音就认为说完了),另外还有一个 5 秒的兜底超时(user_turn_stop_timeout)。

结论:用户说的一整句话,等 VAD + 轮次检测判断"说完了"之后,合并成一条完整消息,一次性发给 LLM——LLM 看到的是完整的一句用户输入,不是碎片。

LLM → TTS:按句子流式分片

LLM 是逐 token 流式吐字的,这些文字先进入 TTS 内部的"分句缓冲区"(TTSService 的 SENTENCE 聚合模式,默认开启)。缓冲区不看时间,只看标点符号(句号、问号、感叹号、分号,以及中文全角标点"。""?""!""；"等)作为切分点——遇到一个完整句子就立刻推给 TTS 合成,不等整段回复说完。

每个句子大约多等 200–300ms 用于攒够一句话,这是"按句切"策略带来的额外延迟。也可以切换成 TOKEN 模式,LLM 吐一个词就立刻扔给 TTS,延迟更低但合成语音的自然度会打折扣(容易断句奇怪)。

打断(Interruption)机制

任意节点可调用 broadcast_interruption() 广播打断信号,同时向上游和下游传播。

  • 下游(TTS / Transport.output):收到后立刻停止播放/丢弃排队中的音频。
  • 上游(LLM / STT):收到后取消正在进行的推理/识别。

EndFrame / StopFrame 等属于不可中断帧(Uninterruptible),即使发生打断也不会从内部队列中被清除。

扩展形态:多 Worker 协作

当需要多个 Worker 协作(如多 Agent 交接、并行辩论)时,还有一层 Bus + Registry + Job 机制。

组件位置作用
WorkerBussrc/pipecat/bus/跨 Worker 消息总线,进程内默认用 AsyncQueueBus,分布式场景用 PgmqBus / RedisBus。
WorkerRegistrysrc/pipecat/registry/Worker 服务发现,watch(name, handler) 监听某个 Worker 就绪。
@job / job_groupsrc/pipecat/pipeline/job_context.py跨 Worker 的请求/响应式 RPC。

这一层是可选的,单机器人语音场景不需要关心,详见 examples/multi-worker/。
